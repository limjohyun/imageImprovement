# PRD: 스마트폰 촬영 이미지 → 고화질 PDF 변환/편집 Tool

## 1. 배경 (Background)

병원 PACS 화면, 온라인 강의 PPT, 온라인 악보 등은 저작권/환경 제약으로 화면을 스마트폰 카메라로 촬영하는 것 외에 원본 파일을 얻을 방법이 없는 경우가 있다. 이렇게 촬영된 이미지는 원근 왜곡, 저조도, 블러, 저해상도 문제로 화질이 나빠 그대로 보관/활용하기 어렵다.

이 도구는 이런 촬영 이미지를 입력받아 인식·보정한 뒤, 더 뚜렷한 PDF로 재생성하고 필요 시 편집까지 할 수 있게 하는 **개인용** 도구다. 배포 목적이 없으므로 라이선스보다 "개인 로컬 환경에서 얼마나 잘 동작하는가"를 우선 기준으로 삼는다.

기술 조사 결과는 `C:\Users\ljohy\.claude\plans\hazy-painting-sonnet.md`에 정리되어 있으며, 본 PRD는 그 결론(언어: Python, 대상 문서 유형 3종 동일 비중)을 그대로 반영한다.

## 2. 목표 (Goals)

- 스마트폰으로 촬영한 문서/화면 이미지를 입력받아 원근 왜곡·기울기·저조도·저해상도 문제를 자동 보정한다.
- 문서 유형(텍스트, PPT 그래프/도형, 악보)을 인식하여 유형에 맞는 후처리를 적용한다.
- 처리 결과를 하나의 PDF로 조립하고, GUI에서 결과를 검수·보정한 뒤 최종 PDF로 저장할 수 있게 한다.
- 텍스트 문서는 검색/복사 가능한 PDF(텍스트 레이어 포함)로 만든다.
- 핵심 파이프라인(전처리~PDF 저장)은 개인 로컬(macOS) 환경에서 오프라인으로 동작한다 (외부 유료 API 의존 없음). 단, §5.8의 클라우드 백업은 사용자가 명시적으로 켠 경우에만 동작하는 선택 기능이다.

## 3. 논-목표 (Out of Scope)

- **배포/제품화**: 다른 사용자를 위한 설치 패키지, 웹 서비스화, 인증/과금 등은 다루지 않는다.
- **PPT 도형의 완전한 재편집(PPTX 생성)**: 원본 PPTX 파일 없이 촬영 이미지만으로 PowerPoint에서 그대로 열리는 편집 가능 도형 객체를 만드는 것은 범위 밖이다. 대신 "선명한 이미지" 또는 "SVG 벡터(색상/선 편집 가능)"까지를 목표로 한다.
- **완전 자동화**: 악보(OMR)와 도형 인식은 오차가 발생할 수 있음을 전제하며, 사람이 검수/보정하는 반자동 워크플로우를 목표로 한다. 100% 무보정 자동 인식은 요구사항이 아니다.
- **모바일 앱**: 촬영은 아이폰 카메라로 하되, 처리/편집 앱 자체는 데스크톱(macOS)에서 동작한다. 촬영 이미지 전달은 파일 복사/폴더 동기화(AirDrop, iCloud 등) 등 기존 수단을 사용한다(자체 전송 기능 불필요).

## 4. 사용자 시나리오

1. 사용자가 PACS 화면, 강의 PPT 슬라이드, 또는 악보를 스마트폰으로 여러 장 촬영한다.
2. 촬영본 이미지 파일들을 도구에 입력(폴더 선택 또는 파일 드래그)한다.
3. 도구가 각 이미지를 자동으로 보정(원근/기울기/조명/해상도)하고, 문서 유형을 인식해 유형별 처리를 수행한다.
4. GUI에서 처리 결과를 페이지 단위로 검수하고, 필요한 경우 수동 보정(자르기, 회전, 텍스트/음표 오류 수정 등)한다.
5. 검수가 끝난 페이지들을 하나의 PDF로 저장한다.

## 5. 기능 요구사항 (모듈 단위)

### 5.1 공통 전처리 (`preprocess`)
세 문서 유형 모두 공통으로 거치는 단계. 조사 결과 §2 참고.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| PRE-1 | 문서 영역 검출 + 원근 보정 | 기울어진 각도로 촬영한 샘플 이미지에서 문서 4모서리를 자동 검출해 정면 뷰로 평탄화한 결과를 출력한다. 자동 검출 실패 시 사용자가 수동으로 4점을 지정할 수 있다. |
| PRE-2 | 기울기 보정(deskew) | 회전된 텍스트/줄이 수평이 되도록 보정한다. |
| PRE-3 | 조명/그림자 보정 | 촬영 시 발생한 그림자·불균일 조명을 완화해 배경이 균일해진다. |
| PRE-4 | 해상도 개선/디노이즈 | 저해상도·노이즈가 있는 입력을 업스케일 처리해 후속 OCR/OMR 인식률이 원본 대비 향상됨을 확인한다. |
| PRE-5 | 파이프라인 재사용성 | 위 4단계는 문서 유형과 무관한 공통 모듈로 구현되어 모든 `processors/*`에서 재사용 가능해야 한다. |

PRE-3 구현 노트: 배경 조도 맵으로 나눈 비율을 0~255로 매핑할 때 적응형 min-max 정규화를 쓰지 않는다. 실사진의 하이라이트·배경 추정 오차로 생기는 이상치 때문에 min-max가 정상 배경(비율 ~1.0)을 어두운 값으로 짓눌러버리는 문제가 실측으로 확인되었다. 대신 비율 1.0(배경)을 흰색 근처로 고정 앵커링하는 고정 스케일(`ratio * 255`, 클리핑)을 써서, 텍스트/악보처럼 어두운 전경 객체 위주인 문서의 흑백 대비가 뚜렷하게 유지되도록 한다.

### 5.2 문서 유형 라우팅 (`router`)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| RT-1 | 유형 분류 | 전처리된 이미지를 텍스트/도형/악보 중 하나로 분류(자동 추정 + 수동 오버라이드 가능)한다. |
| RT-2 | 처리기 라우팅 | 분류 결과에 따라 해당 `processors/*` 모듈로 전달한다. |

### 5.3 텍스트 처리 (`processors/text.py`)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| TXT-1 | OCR 인식 | 한국어/영어 혼용 텍스트를 인식한다. |
| TXT-2 | 검색 가능한 PDF 생성 | OCRmyPDF 방식으로 이미지 위에 투명 텍스트 레이어를 얹어, 최종 PDF에서 텍스트 검색·복사가 가능하다. |
| TXT-3 | 인식 오류 검수 | GUI에서 인식된 텍스트를 확인/수정할 수 있다. |

### 5.4 도형/그래프 처리 (`processors/diagram.py`)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| DIA-1 | 선명화 | 저해상도 도형 이미지를 확대해도 윤곽이 뭉개지지 않는 수준으로 출력한다. |
| DIA-2 | 벡터화(옵션) | 사용자가 요청 시 SVG 벡터로 변환해 선/색상을 편집 가능하게 한다. |
| DIA-3 | 한계 고지 | PPTX로 완전 재편집되는 결과가 아님을 GUI 상에서 명확히 안내한다 (§3 참고). |

| ID | 요구사항 | 수용 기준 |

### 5.6 PDF 조립 (`pdf_assembly`)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| PDF-1 | 다중 페이지 조립 | 여러 장의 처리 결과(텍스트/도형/악보 혼합 가능)를 순서대로 하나의 PDF로 합친다. |
| PDF-2 | 페이지 재정렬/삭제 | GUI에서 최종 조립 전 페이지 순서 변경, 삭제가 가능하다. |

### 5.7 GUI (`gui`)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| GUI-1 | 입력 | 폴더/다중 파일을 선택해 일괄 입력할 수 있다. |
| GUI-2 | 미리보기 | 원본과 처리 결과를 나란히 비교해 볼 수 있다. |
| GUI-3 | 수동 보정 | 자르기/회전 등 기본 보정과, 유형별 검수(§5.3~5.5)를 수행할 수 있다. |
| GUI-4 | 내보내기 | 최종 PDF를 지정 경로에 저장한다. |

### 5.8 선택적 클라우드 백업 (`backup`, 선택 기능)

기본 워크플로우는 항상 로컬 완결이며, 이 모듈은 사용자가 명시적으로 활성화했을 때만 동작하는 부가 기능이다. Supabase(Storage + Postgres)를 백업 대상으로 사용한다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| BKP-1 | 로컬 저장 우선 | 백업 기능 활성화 여부와 무관하게 PDF-1/GUI-4의 로컬 저장이 항상 먼저 완료된 뒤에만 백업이 시도된다. 백업 실패가 로컬 저장 결과에 영향을 주지 않는다. |
| BKP-2 | 활성화 시 업로드 | 사용자가 설정에서 백업을 켠 경우, 완성된 PDF를 Supabase Storage 버킷에 업로드하고 파일명·문서 유형·생성일시·Storage 경로를 Supabase Postgres 테이블에 기록한다. |
| BKP-3 | 오프라인 동작 보장 | 백업이 꺼져 있거나 네트워크가 없을 때도 핵심 파이프라인(§5.1~§5.7)은 100% 오프라인으로 동작해야 한다. 네트워크 오류는 백업 단계에서만 사용자에게 알리고 나머지 흐름을 막지 않는다. |
| BKP-4 | 자격증명 관리 | Supabase URL/API 키는 코드에 하드코딩하지 않고 로컬 설정 파일(예: `.env`, git에는 커밋하지 않음)로 관리한다. |

## 6. 단계별 우선순위 (Phase)

로드맵 세분화(Shrimp Task Manager)의 기준선으로 아래 순서를 제안한다. 각 Phase는 이전 Phase의 공통 모듈을 재사용한다.

- **Phase 1**: 공통 전처리(`preprocess`) + 텍스트 처리(`processors/text.py`) + 최소 GUI(입력→미리보기→PDF 저장) — 가장 검증된 경로(OpenCV+OCRmyPDF)로 end-to-end 파이프라인을 먼저 완성.
- **Phase 2**: 도형/그래프 처리(`processors/diagram.py`) 추가.
- **Phase 3**: 악보 처리(`processors/score.py`) 추가 (OMR 오차가 가장 크므로 검수 UX를 함께 설계).
- **Phase 4**: GUI 고도화(검수/수동 보정/페이지 재정렬 등 §5.7 전체) 및 유형 자동 라우팅(`router`) 정교화.
- **Phase 5 (선택, 낮은 우선순위)**: 선택적 클라우드 백업(§5.8) — 핵심 파이프라인이 안정된 뒤에 부가 기능으로 진행.

## 7. 기술 스택 (조사 결과 §1 요약)

- 언어: Python 3.11+
- 이미지 처리: OpenCV, Real-ESRGAN
- OCR: PaddleOCR 또는 Tesseract + OCRmyPDF
- 벡터화: VTracer
- 악보: oemer (필요 시 Audiveris 대안 검토)
- PDF: PyMuPDF, img2pdf, ReportLab
- GUI: PySide6
- 백업(선택, Phase 5): `supabase-py` (Supabase Storage + Postgres)

## 8. 리스크

- **OMR/도형 인식 정확도**: 완벽한 자동 인식은 불가능 → 검수 UX가 핵심 요구사항 중 하나로 취급되어야 함(§5.3~5.5의 검수 항목).
- **무거운 ML 의존성**: Real-ESRGAN/PaddleOCR 등은 PyTorch 등 대형 패키지를 요구 → 개발 환경 설치 부담이 큼(별도 설치 목록 안내 참고).
- **PPTX 완전 재현 기대치 오해**: 사용자가 "PPT처럼 완전 편집 가능"을 기대할 경우 실망 가능 → §3에서 명시적으로 범위를 한정.
- **오프라인 목표와 클라우드 백업의 충돌**: Supabase 백업(§5.8)은 인터넷/계정이 필요해 목표 §2의 오프라인 원칙과 상충될 수 있음 → 항상 opt-in 부가 기능으로 두고(BKP-1~3), 기본값은 꺼짐으로 유지해 리스크를 완화한다.

## 9. 검증 방법

- Phase 1 완료 시: 왜곡·저해상도 샘플 이미지 1장을 입력해 검색 가능한 PDF가 생성되는지 end-to-end로 확인.
- Phase 2/3 완료 시: 각각 도형/악보 샘플로 동일한 end-to-end 확인.
- Phase 4 완료 시: GUI에서 여러 유형이 섞인 입력 세트로 전체 워크플로우(입력→검수→조립→저장)를 수행.
- Phase 5 완료 시: 백업을 끈 상태에서 네트워크를 차단하고 전체 워크플로우가 정상 동작하는지 확인(BKP-3), 백업을 켠 상태에서 Supabase Storage/DB에 파일과 메타데이터가 기록되는지 확인(BKP-2).
